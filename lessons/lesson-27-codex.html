本课导读模块三

第 26 次课练的是「把一件事说具体、说得可验收」。 这一课把同一套本事用在代码上：让 AI 真的打开你的项目、改掉一个文件、再交给你验收。 用的工具是 Codex——OpenAI 面向软件开发任务的编程智能体（官方术语表口径，本站核对日期 2026-09-26）。

它和普通聊天的区别只有一句：聊天给你一段代码，Codex 直接动你的文件。 它能读你的项目、提出修改、运行检查——方便是真的方便，但你得先在心里划一条线： 它能碰哪些文件、这次只改哪一处、改完你拿什么验收。

现象卡在哪
它给的代码很漂亮，复制过去跑不起来它没看过你的项目——不知道你有什么文件、用的什么写法
它说「已完成」，页面上却什么都没变没有人真的打开页面去看；「它说做完了」和「它做对了」是两件事
改了标题，顺手把样式也换了一遍指令里没写「不要改其他文字和样式」，它就按自己的审美发挥了
不敢用，怕它动坏别的文件夹没给它划范围。先在副本里练一次，比在心里担心一百次有用
提前说清楚 本课只有一个任务，全程只在一处动手：用 Codex 打开课堂安全副本 lesson27-demo，把首页标题「我的课程作品」改成「我的AIGC课程作品」。
三条红线先立住：不装依赖、不删文件、不联网发布； 四类东西不提交：密钥、Cookie、个人路径、未经核验的代码。
两个实操前后相接：① 拿到一份「只碰 index.html 一处」的修改计划， ② 按计划执行、保存、打开页面验收。走完你手上会有改动前后两张截图 + 一句验收结论。

本课涉及的产品口径取自 OpenAI 官方 Codex 文档与术语表，核对日期 2026-09-26； 界面、命令与参数随版本更新，以你实际使用的版本为准。
课内的练习网页、目录结构与截图示例全部为教学示意，用于讲清方法，不是任何真实项目。

学习目标

学完这一课，你应该能——

  1. 说出 Codex 的 CLI 与桌面端各自长什么样，并说出两者共同的四个动作：读项目、提修改、跑检查、交给你复核；
  2. 按「先报结构、再定目标文件」的顺序，让它在动手前先把仓库结构说清楚；
  3. 按四要素（改哪个文件 / 改哪一处的什么 / 不许碰什么 / 怎么验收）写出一条小任务指令；
  4. 看懂它给出的修改计划，判断这份计划是不是只碰了你要改的那一处，不对就立刻叫停；
  5. 在安全副本里走完「提出 → 看计划 → 执行 → 打开页面验收」四步，交出截图与一句验收结论；
  6. 说出三条红线和四类不能提交的东西，并说清为什么测试通过了还要自己打开页面看一眼。

一、同一个搭档的两张脸：CLI 与桌面端开局

第一次搜 Codex 教程，你会看到两种画风：一种是全黑的窗口，一行行敲命令； 另一种有窗口、有点按钮的界面，左边项目、中间对话、右边结果。 很多人以为这是两个软件，其实只是同一个编程智能体的两种外壳。

按 OpenAI 官方口径，Codex 有 CLI（终端）、桌面应用、云端、IDE 扩展四种形态； 本课只用前两种。CLI 靠文字命令工作，桌面端提供可视界面—— 换的是「你怎么说」，不是「它能干什么」。

维度CLI（终端）桌面端
怎么进入在项目目录里敲 codex，一个黑窗口就是全部界面打开应用，选中一个项目文件夹再开始对话
你怎么说一行命令或一段粘贴进去的文字在输入框里打字，和聊天类似
它怎么回逐行往下滚：读到哪些文件、打算怎么改、要不要你确认同样分栏显示：计划、改动的文件、变更清单
新手感觉吓人，但每一步都写在屏幕上，反而更容易回看亲切，但按钮多了容易一路点下去，忘了看计划
共同点都能让 AI 读取项目、提出修改、运行检查；都要你确认之后才真的改文件

CLI 需要先装 Node.js，再用 npm 全局安装；第一次运行会让你登录， 常见是ChatGPT 账号登录或 API 密钥登录两种（新手优先用账号登录）。

二、仓库—结构—小任务：先看清再开口方法

最常见的翻车方式是这个：你把一段代码贴给它，问「这段怎么改」。 它给出了非常专业的答案——但改的文件你项目里根本没有， 因为从头到尾没人告诉它你的项目长什么样。

词是什么你要先确认什么
仓库一个项目的文件集合——就是那个文件夹它打开的是不是这一个文件夹（CLI 里看命令行路径，桌面端看左下角）
目录结构这个文件夹里有什么、在哪个子目录让它先报一遍结构，别让它猜
目标文件这次要动的那个文件说清文件名，不要说「首页」这类它得猜的词
小任务只改一个明确位置的任务你能一句话说清改了哪个文件的哪一处

所以动手前的第一句话不该是「帮我改一下」，而是「先说说这个目录里有什么，先别改」。 

请先只列出当前目录的文件与目录结构，不要修改任何文件，也不要运行命令。
列完告诉我：如果要改首页的大标题，应该改哪个文件、哪一行的什么内容。

它回的结构大致是这样（教学示意）：

lesson27-demo/
├── index.html      ← 首页，标题写在 h1 里
└── styles.css      ← 样式，标题的颜色和字号在这里
小任务的判据只有一句 问自己：我能不能一句话说清「改了哪个文件的哪一处、为什么要改、可能影响什么」？ 能说清，就是小任务，可以放手让它做；说不清，说明范围还没定，先缩小再说。
小任务的好处不是快，是好回滚——只改一处，改坏了退回去也是一秒钟的事。

三、一条能验收的指令怎么写本课核心

核心案例的问题就一句：让 AI 改代码之前，最该提供什么信息？ 下面三句话要的是同一件事，你猜它会给出三种什么计划。

可运行演示 ② 同一件事的三种说法，计划质量差多少
—计划里要改几处
—要不要你回头补救
—能不能一句话回滚
教学示意，非实测数值。三版指令与三份计划均为讲课用示意， 用来演示四要素写全前后的差别，不是某个真实项目的执行记录。

四要素：写全了就不用猜

要素写什么本课这一条
① 改哪个文件文件名，必要时带上路径index.html
② 改哪一处的什么原来的文字 → 改成什么首页标题「我的课程作品」→「我的AIGC课程作品」
③ 不许碰什么红线写死，别让它发挥不要改其他文字和样式，不要动 styles.css
④ 怎么验收做完看什么、什么算对双击打开 index.html，标题变了且样式正常
动手做 ①·在安全副本里提一处改动，拿到一份「只碰一处」的修改计划 本课主体

做完你手上会有：一份 lesson27-demo 副本（改动前的样子）、 Codex 报出的目录结构、以及一份只涉及 index.html 一处标题的修改计划 （外加你自己的一句核对结论）。

第 3 步 · 先让它报结构，别急着提改动

  1. 把下面这段原样发进去 这一步是在确认「它看到的项目和你看到的是同一个」。
请先只列出当前目录的文件与目录结构，不要修改任何文件，也不要运行命令。
列完告诉我：如果要改首页的大标题，应该改哪个文件、哪一行的什么内容。

第 4 步 · 提出这一处小改动

  1. 把下面这段指令整段发进去 整段粘贴，不要自己改写——四要素是一套的， 删掉「不要改其他文字和样式」，它就会顺手改样式。
请先说明要修改哪个文件，再把首页标题"我的课程作品"改为"我的AIGC课程作品"；不要改其他文字和样式。

第 5 步 · 读它给的计划，只认「一处」

计划出来后，对着这三条核一遍：

查什么合格的样子
改的是不是 index.html文件名是 index.html，不是别的
改了几处只有标题那一处；多出一处就要问为什么
有没有越界动作没有删除文件、没有安装依赖、没有联网发布

做到这三条，就算做完了

  1. 它的计划里写清了「改 index.html」，并且只改了标题这一处 改了三处说明它把「标题」理解成了所有出现这个词的地方。
    它改多了：补一句「只改 h1 里那一处，其他位置的相同文字一律不动」。
  2. 计划里没有删除、安装依赖、联网发布这三类动作 出现任何一条，立刻停止，不要点同意。
    它要装东西：回一句「本次任务不许安装任何依赖、不许联网，只做这一处文字替换」。
  3. 你能指着计划说出「改了哪个文件的哪一处、为什么」 说不出来，说明这份计划你没真看懂，先让它用大白话复述一遍。
    看不懂计划：补一句「用三句话说明你要改什么、怎么改、会影响什么，不要贴代码」。

要交的成果：这份修改计划（截图即可）+ 改动前的页面截图。下一步就是让它真的动手。

「先说明要改哪个文件」不是客套 这句是在给它一个定位锚：它先说文件名，就等于先承认了「我要动的是这个文件」。 后面它要是越界改了 styles.css，你就有据可依地叫停。
少了这一句，它很可能顺手「优化一下样式」——你没要求，但它觉得更好。

四、跑测试与复核：它说做完了不算收口

「它说已完成」「测试全绿」，这两件事都不能代替最后一步：你自己打开页面看一眼。 测试只能证明「代码没写错」，证明不了「你要的效果实现了」—— 标题改在了另一个文件里，测试一样会绿。

手段能发现什么发现不了什么
运行测试 语法错、引用错、跑不起来的地方 改错了文件、改多了地方、效果跟你要的不一样
看变更清单 它到底动了哪几个文件、改了哪几行 页面上看起来对不对（清单不会告诉你观感）
人工复核
打开页面 / 看输出		 目标是不是真的实现了、样式有没有被带偏 看不见的隐患（例如顺手改了某个公共函数）

动手做 ②·让它执行这一处修改，保存，打开页面验收 本课收口

做完你手上会有：改好的 index.html、 改动后的页面截图，以及一句说清「改了哪个文件、页面上看到什么」的验收结论。

第 1 步 · 同意执行，只让它做这一处

  1. 把下面这段原样发进去 注意最后那句「不运行任何其他命令」—— 这是防止它为了「顺手检查一下」去装东西。
按上面的计划执行：只改 index.html 里那一处标题，保存文件。
不要运行任何其他命令，不要修改 styles.css 和其他文件，不要联网发布。
改完后告诉我：改了哪个文件的哪一行、改动前后分别是什么。

第 2 步 · 打开页面验收（这一步不能省）

  1. 双击副本里的 index.html 在浏览器里看两件事：大标题是不是变成了「我的AIGC课程作品」、 蓝色头部和卡片样式是不是还正常。
  2. 再回到 Codex，让它把改动前后摆出来给你核 把下面这段发进去，它的回答就是你要核的三件事。
请列出本次的全部改动：文件名、改动位置、改动前的原文、改动后的新文。
同时说明：有没有动过 styles.css，有没有运行过任何命令。
不知道的写【待确认】，不许推测。

第 3 步 · 让它写出那句验收结论，你来核

  1. 把下面这段紧接着发出去 结论由它起草、由你签字：它写的内容必须和你刚才在页面上看到的完全一致。
用一句话写验收结论，必须包含三样：改了哪个文件的哪一处、
页面上看到的变化、样式有没有受影响。
不要写"已完成""处理完毕"这类没有信息量的话。

做到这三条，就算做完了

  1. 浏览器里的大标题已经变成「我的AIGC课程作品」，且蓝色头部、卡片样式没变 标题变了但样式乱了，说明它顺手动了 styles.css。
    样式被改了：发一句「把 styles.css 恢复到改动前，只保留 index.html 的标题改动」。
  2. 它列出的改动只有 index.html 一处，且明确说了没动 styles.css、没跑命令 列出两处以上，就是计划阶段没卡住。
    它含糊其辞：补一句「逐条列出每个被修改的文件，没有也要写明『未修改 styles.css』」。
  3. 那句验收结论里，文件名、改动位置、页面变化三样都说到了 只写「已完成」的，退回让它按三样重写。
    它写得太虚：把上面那段指令再发一次，并补一句「必须出现 index.html 这个文件名」。

要交的成果：改动前后两张截图 + 一句验收结论。

红线：三件事一旦出现，立刻停止 ① 要删除文件——你让它改标题，它为什么要删东西？
② 要安装依赖——一个文字替换不需要装任何东西；
③ 要联网发布——练习副本不属于任何线上站点。
这三类动作出现在计划里，不同意、不继续，重新交代约束后再来一次。

五、三条红线与数据边界底线

Codex 和聊天机器人最大的不同，是它手上有权限：能读你的文件、能改你的文件、能跑命令。 权限是它好用的原因，也是它危险的原因。

它能做对应的风险本课怎么限制
读取项目文件你把整个盘或整个桌面给它，它就能读到所有东西只打开 lesson27-demo 这一个副本目录
修改并保存文件改多了、改错了地方，原文件被覆盖小任务：只改一处；改前看计划，改后看变更
运行命令装依赖、删文件、联网发布，都可能在这一步发生指令里写死「不运行任何其他命令」
联网你的代码和文件内容可能被送到模型服务端不提交密钥、Cookie、个人路径；练习副本不放真实资料
 
1. 密钥与令牌：API Key、Access Token、密码
2. Cookie 与登录态：浏览器里的登录信息、会话串
3. 个人路径与身份信息：含真实姓名/学号的绝对路径、身份证号、手机号
4. 未经核验的代码：别人给的、来源不明的、看不懂在干什么的代码
一句话记住本课 操作原则是先确定目标和范围，再使用工具； 完成后检查三样：内容准不准、范围对不对、能不能保存交付。
你不是不敢用，是先在副本里用一次，把边界摸清楚。

本课要点回顾

这一课要带走六件事

  1. Codex 是面向软件开发任务的编程智能体；CLI 敲命令、桌面端有界面，外壳不同、四步相同；
  2. 开口前先看结构：仓库 → 目录结构 → 目标文件 → 小任务，先让它报结构再提要求；
  3. 指令四要素：改哪个文件 / 改哪一处的什么 / 不许碰什么 / 怎么验收，后两条最容易漏；
  4. 计划阶段是唯一能在文件被改之前叫停的机会：只认一处，越界就停；
  5. 测试通过≠做对了。最后一环永远是人工复核：打开页面看 + 让它列出全部改动；
  6. 三条红线 不装依赖、不删文件、不联网发布；四类东西不提交：密钥、Cookie、个人路径、未核验代码。

下一步棋：今天我们靠划范围来保证安全——只给它一个副本目录、只让它改一处。 下一课 Hermes-Agent 换个角度： 一个会记住你、会自己攒技能的助手，带来的是另一种便利和另一种风险。 今天练的「先定范围、再看计划、最后人工验收」，在那儿会变成一句更关键的话—— 哪些事它可以记住，哪些事它绝对不能记住。

本页产品口径取自 OpenAI 官方 Codex 文档与术语表，核对日期 2026-09-26； 课内练习网页、目录结构与命令输出为教学示意，界面与命令随版本更新，以实际版本为准。

课后作业单选 / 多选 / 判断

1.（单选）关于 Codex 的 CLI 与桌面端，说法正确的是？
A. 两个不同产品，能力差别很大
B. CLI 只能聊天，改文件必须用桌面端
C. 同一个编程智能体的两种外壳，共同点是都能读项目、提修改、跑检查
D. 桌面端不需要联网，所以一定更安全
【答案】C
【解析】两者只是交互方式不同：CLI 靠文字命令，桌面端提供可视界面，底层都能读取项目、提出修改、运行检查并交给你复核。B 说反了；D 不成立，安全性取决于授权范围与配置，不是界面形态。

2.（多选）一条"能验收"的改动指令，应当写全哪些要素？
A. 改哪个文件
B. 改哪一处的什么内容
C. 不许碰什么
D. 怎么验收（做完看什么）
【答案】ABCD
【解析】四要素缺一不可。实务中最容易漏的是 C 和 D：不写"不许碰什么"，它就会顺手改样式；不写"怎么验收"，事后你就没法判断它做没做对。

3.（单选）它给出的修改计划里出现"安装一个依赖包"，正确的做法是？
A. 同意执行，装完再看效果
B. 立刻停止，重新交代"本次不安装任何依赖"
C. 换个模型重试一遍
D. 先让它装，装完再卸载
【答案】B
【解析】改一处文字不需要任何新依赖，出现这条说明它自己扩大了任务范围。计划阶段是唯一能在文件被改之前叫停的机会，属于本课三条红线之一。C 没解决问题，A、D 都是在赌。

4.（判断）测试全部通过，就可以确认这次改动已经成功。
A. 正确
B. 错误
【答案】B（错误）
【解析】测试只能证明代码没写错，证明不了你要的效果实现了——改动落在另一个文件里，测试一样是绿的。最后一环必须是人工复核：打开页面看效果，并让它列出全部改动清单逐条对。

5.（多选）下面哪些做法符合"小任务"的要求？
A. 一次只改一个明确位置，说清改了哪个文件的哪一处
B. 把整个桌面交给它，方便它自己找文件
C. 先在副本目录里练，不碰真实项目
D. 改完之后打开页面看一眼，再让它列出全部改动
【答案】ACD
【解析】B 违反"授权范围划得越小越好"——它既能读又能改，范围一大风险就不可控。ACD 分别对应小任务的定义、安全副本的做法和人工复核的要求。

6.（多选）下列哪些内容不该出现在交给 Codex 的材料里？
A. API Key 之类的密钥与令牌
B. 浏览器里的 Cookie 与登录态
C. 含真实姓名或学号的个人路径
D. 课堂安全副本里的练习网页
【答案】ABC
【解析】密钥、登录态、个人路径与身份信息属于任何时候都不提交的四类内容。D 恰恰是推荐做法——练习副本就是为了让你放心练手，前提是副本里不放真实资料。
评分看什么 本课作业按三处判断：一是能否分清「外壳不同、四步相同」，不把 CLI 与桌面端当成两种能力； 二是提到指令时，是否意识到「不许碰什么」和「怎么验收」这两条最容易被漏； 三是验收环节，是否把人工打开页面看一眼当成必须动作，而不是相信「已完成」三个字。
